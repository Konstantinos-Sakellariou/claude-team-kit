# Design Reference

## What The Design Team Is

The `Design Team` is the reusable domain pack for product UX, UI layout, design-system consistency, and brand-sensitive visual work.

It exists so design-heavy work does not get treated as:
- generic product planning
- generic writing
- generic frontend implementation
- or ad hoc visual tweaking with no real owner

## Why A Design Team Is Needed

As this kit moves toward product-building and company-building support, design quality becomes first-class.

That means we need a stronger answer for work such as:
- app flows and screen structure
- onboarding and trust-critical UX
- landing pages and hero surfaces
- reusable component and token guidance
- brand coherence across product and marketing surfaces

Without a design owner, the repo tends to get:
- uneven visual quality
- weak hierarchy
- improvised heroes and layouts
- one-off UI decisions that never scale

## What The Design Team Should Cover

Use the `Design Team` when the work is mainly about:
- product-surface UX and user flow clarity
- dashboard, app, or website layout direction
- visual hierarchy and interface polish
- design-system consistency
- brand or presentation credibility

Typical lead split:
- `@product-designer` for UX, app flows, and screen structure
- `@brand-designer` for identity-sensitive presentation and visual direction

Typical supporting roles:
- `@ui-designer`
- `@design-systems-architect`
- `@customer-advocate`
- `@product-owner`

## Design Team Vs Other Teams

- `Advisory Review Team`
  - use when the problem is mostly product scope, prioritization, or strategic fit
- `Engineering Team`
  - use when the work is mainly implementation rather than UX or visual direction
- `Content & Publishing Team`
  - use when the main output is written content rather than UI or layout

The `Design Team` fits when the primary question is:
- what should this surface feel like?
- how should it be structured?
- what makes it clearer, stronger, or more trustworthy?

## Good Outcomes

A good design-team pass should leave:
- a clearer primary user goal
- stronger hierarchy and layout direction
- fewer one-off visual decisions
- better trust and readability
- clearer handoff into implementation

## Current Follow-Up

The immediate repo-specific follow-up after adding the team is:
- re-check the README hero and broader brand/layout quality with the new design capability in place

## Design Team And Design Packs

The `Design Team` owns the judgment layer.

Design packs are the reusable starting layer that can help the team begin from:
- a stronger visual direction
- a reusable brand/system baseline
- an optional `DESIGN.md` brief when that artifact is helpful

Use the team for decisions.
Use design packs for stronger defaults.

The first reusable design-pack library now covers:
- clean SaaS product
- startup studio / founder service
- premium service / advisory
- technical console / dashboard
