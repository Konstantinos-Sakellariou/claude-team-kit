# Vision Template

Use this file as the starter for a local, repo-specific vision at `docs/VISION.md`.

Recommended model:
- keep `docs/VISION.example.md` tracked as the public template
- keep your real `docs/VISION.md` local if it contains strategy, company direction, product bets, or private operating intent

This template exists so the kit teaches the concept of a vision document without forcing your actual strategy into git history.

## Purpose

Use a local vision doc to answer:
- why this repo exists
- what product or company direction it supports
- what it should and should not become
- how future additions should be judged

## Suggested Structure

### Why This Repo Exists

Describe the core purpose of the repo in one short paragraph.

### Product Or Operating Vision

Explain the larger destination:
- what you are building
- what operating model you are aiming for
- what this repo should eventually help you run

### What This Repo Should Be

- [Example capability or role]
- [Example capability or role]
- [Example capability or role]

### What This Repo Should Not Become

- [Boundary or anti-goal]
- [Boundary or anti-goal]
- [Boundary or anti-goal]

### Core Principles

List the design principles that should shape future work.

Examples:
- reusable over project-specific
- visible over magical
- durable over chat-only
- private-safe by design
- lean hot path, deep linked docs

### Who This Is For

Describe the primary users and, if useful, the future users.

### What Success Looks Like

Describe what “working well” looks like in practice.

### Near-Term Priorities

List the most important next priorities for the repo or product.

### Long-Term Horizon

Describe the larger destination, but keep it grounded.

### Vision Alignment Rule

State how new backlog items, plans, teams, or features should be checked against the vision.

### Working Vision Statement

Write one short final statement that captures the intended direction.

## Practical Guidance

- keep the real vision sharp, not bloated
- let the vision drive roadmap sequencing and backlog shaping
- put detailed implementation in plans, not in the vision doc
- keep private strategy local unless you explicitly want it tracked
