# Agent SDK User Input Integration Plan

## Idea Summary

Evaluate how Claude Code Agent SDK user-input handling can improve `claude-team-kit`, especially for:
- guided initialization
- requirement gathering
- approvals
- safer, friendlier multi-step workflows

This is about the SDK feature described in Claude Code docs for `canUseTool` and `AskUserQuestion`, not a prompt-only trick.

## What The Feature Actually Is

The Agent SDK lets a host application intercept:
- tool approval requests
- clarifying questions generated by Claude through `AskUserQuestion`

The host app then:
- presents those questions or approvals to the user
- collects the answers
- returns them to Claude so work can continue

Important boundary:
- this is an SDK/runtime integration capability
- it is not something a markdown-only workspace kit can enable by itself

## Why It Fits This Repo

This fits `claude-team-kit` well because the repo is increasingly moving toward:
- friendlier bootstrap and guided initialization
- clearer approvals
- higher-quality requirement gathering
- future product/app surfaces on top of the workspace model

It is especially aligned with:
- `@master` guided initialization
- new-repo bootstrap
- command flows like `/bootstrap-repo`, `/plan-idea`, and `/release-check`
- future app/productization work in the roadmap

## Where It Adds Real Value

### 1. Guided Initialization

Instead of relying only on free-form chat, a future SDK-backed host could let `@master` ask structured clarifying questions during repo bootstrap.

Examples:
- what kind of product is this?
- which stack family is closest?
- do you want private or public backlog mode?
- should this repo use local context?

### 2. Approval-Gated Workflows

This can make approvals feel cleaner and safer in:
- ADR saving
- plan saving
- release checks
- Git/GitHub flows
- repo cleanup

### 3. Better Productization

If this kit later becomes an app or richer local interface, this feature is one of the cleanest ways to make the system feel interactive without turning everything into fragile prompt choreography.

## Why It Should Not Be Pretended Into The Core Today

The core repo should not claim to "support" SDK-style user-input callbacks unless a real host app or SDK integration exists.

Without the SDK host layer:
- `AskUserQuestion` is not actually available
- prompt-only questioning is still useful, but it is not the same feature
- pretending otherwise would blur a real product boundary

So the right approach is:
- keep prompt-based guided initialization in the core
- add SDK user-input integration as an optional future compatibility layer

## Recommended Integration Model

### Phase 1: Documented Compatibility Target

Add documentation explaining:
- how this feature maps onto `@master` guided initialization
- which workflows would benefit
- what a future SDK host must implement

No runtime changes required yet.

### Phase 2: Prompt Design Alignment

Refine `@master` so its guided questions are easier to map into structured multiple-choice or small-batch user-input flows later.

Good candidates:
- bootstrap questions
- backlog mode selection
- local-context opt-in
- cleanup confirmation
- Git/GitHub go/no-go gates

### Phase 3: Optional SDK/App Integration Layer

If this repo gains:
- a real SDK wrapper
- a local app
- or an app-backed orchestration shell

then implement:
- `canUseTool` handling
- `AskUserQuestion` support
- approval UI for sensitive tools
- structured question UI for bootstrap and planning

## Concrete Fit With Existing Repo Features

Best future connection points:
- `@master` bootstrap and guided initialization
- `@master` reporting and approval surfaces
- command layer
- roadmap/productization work
- cleanup and backlog persistence flows

Less useful areas:
- generic low-level code edits
- purely local tactical work where plain chat is already enough

## Risks

- over-designing around a runtime feature that does not exist in this repo yet
- confusing prompt-based questions with SDK-backed structured input
- adding docs that imply support before there is a host integration

## Success Criteria

This is worth pursuing only if it clearly:
- makes the kit easier to use for non-expert users
- improves bootstrap and planning quality
- reduces ambiguity in approval-heavy flows
- fits future app/productization work without bloating the core

## Recommendation

Yes, this is a good fit.

But it is a fit as:
- a future SDK/app integration layer
- a prompt-design target for `@master`
- a productization enabler

It is not a reason to claim new runtime capabilities inside the current markdown-only core.
